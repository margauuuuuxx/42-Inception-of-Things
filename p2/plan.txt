Deployment: manages Pods via a ReplicaSet (auto-created, not manually written)

Deployment/Service files inside p2/confs/, one file per app (app1.yaml, app2.yaml, app3.yaml)
    each containing a Deployment + Service, separated by "---"
    --> will be applied via kubectl apply -f in the provision script

    result --> deployment.apps/<name> created, service/<name> created
    (the resource kind + API group in the output depends on the "kind" defined in each YAML document)

accessing app3 (default) in a browser in ssh:
    http://192.168.56.110:80
    --> bare IP access always lands on app3, because no Host header matches app1.com/app2.com,
        so Ingress falls through to the default backend

accessing a specific app in the terminal via its virtual hostname in ssh:
    curl -H "Host: app1.com" http://192.168.56.110:80
    --> curl and the browser method are two independent, alternative ways of setting the
        same Host header -- not used together

Ingress = host-based virtual hosting:
    one IP:port serving multiple distinct apps; the Host header text is the only thing
    that decides which app answers

Service load balancing (across replicas of ONE app, e.g. app2's 3 pods) is a different layer
from Ingress routing (deciding WHICH app/Service a request goes to, based on Host header)
    --> Ingress implemented by Traefik in K3s
    --> Ingress rule: host: field for app1.com and app2.com, default backend for app3
